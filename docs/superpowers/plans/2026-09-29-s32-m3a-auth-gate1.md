## 0. Goal

Replace the two normal human browser token prompts with one Google-authenticated BOOK-ID-SEARCH session while preserving existing bearer-token compatibility.

Current browser secrets:
- WeRead: `book-id-search:weread-private-token` → `WEREAD_PRIVATE_API_TOKEN`
- S32: `book-id-search:s32-private-token:v1` → `S32_PRIVATE_API_TOKEN`

Target:
- human browser → Google login → BOOK-ID-SEARCH session cookie;
- machine/admin/acceptance → existing bearer token paths remain valid.

No ResearchRun/Dossier implementation in Gate 1.

## 1. Runtime/config contract

Add API configuration:

```text
GOOGLE_AUTH_ENABLED=true
GOOGLE_CLIENT_ID=<web OAuth client id>
BOOK_ID_SEARCH_OWNER_GOOGLE_SUB=<verified Google sub>
BOOK_ID_SEARCH_SESSION_SECRET=<random high-entropy secret>
BOOK_ID_SEARCH_PUBLIC_ORIGIN=https://books.conanxin.com
```

Rules:
- if Google auth is disabled, existing bearer flows continue unchanged;
- if enabled but required config is missing, auth endpoints fail closed;
- never put session secret / owner sub in Vite variables;
- Web may receive only public Google client ID.

Web build config:

```text
VITE_GOOGLE_CLIENT_ID=<same public web client id>
```

## 1.1 Plan review corrections

- Web dev server already proxies `/api` to `127.0.0.1:3001`, so browser auth can remain same-origin in local development as well as production.
- Do **not** treat the existing global `cors()` middleware as an authorization or CSRF boundary.
- Production cookie name: `__Host-book_id_search_session`, with `Secure`.
- Local HTTP dev cookie name: `book_id_search_session_dev`, without the `__Host-` prefix and without `Secure`; still HttpOnly / SameSite=Lax / Path=/.
- Cookie-authenticated unsafe requests must independently require exact configured Origin + session CSRF nonce.
- Google login uses GIS JavaScript callback → same-origin JSON POST. If a future implementation switches to GIS direct `login_uri` POST, adopt Google's double-submit `g_csrf_token` contract for that flow.
- Private session responses must not enable wildcard credentialed CORS. Normal Web use remains same-origin.

### 2.1 Google ID-token verification

Use `google-auth-library` on the server.

Verification requirements:
- signature valid;
- audience == configured `GOOGLE_CLIENT_ID`;
- issuer valid;
- token not expired;
- `sub` present;
- verified `sub` == configured owner sub.

Do not treat email as the durable principal.

No Gmail API scopes.

### 2.2 Session cookie

Cookie names:
- production: `__Host-book_id_search_session`;
- local HTTP development: `book_id_search_session_dev`.

Attributes:
- HttpOnly;
- Secure in production;
- SameSite=Lax;
- Path=/;
- no Domain.
- Production must satisfy the `__Host-` cookie requirements; development must not pretend an insecure HTTP cookie is a production `__Host-` cookie.

Signed payload v1:

```json
{
  "v": 1,
  "sub": "...",
  "email": "...",
  "iat": 0,
  "exp": 0,
  "csrf": "random..."
}
```

HMAC-SHA256 with `BOOK_ID_SEARCH_SESSION_SECRET`.

v0.1 TTL recommendation: 8 hours.

No DB/session table in this gate.

### 2.3 CSRF

Cookie-authenticated unsafe methods (POST/PUT/PATCH/DELETE) require:
- exact allowed `Origin` == `BOOK_ID_SEARCH_PUBLIC_ORIGIN`;
- `X-CSRF-Token` equal to the nonce embedded in the signed session.

`GET /api/auth/session` returns the CSRF nonce to authenticated same-origin Web JS.

Bearer-token authenticated requests remain compatible and do not require browser CSRF headers.

Google sign-in submission:
- Web receives Google credential via GIS callback;
- same-origin JSON `POST /api/auth/google`;
- require exact configured Origin and JSON content type;
- verify Google ID token server-side;
- issue session cookie.
- The current design does not use GIS direct `login_uri` POST. If that changes, implement the Google-provided double-submit CSRF cookie/parameter contract.

## 3. Auth endpoints

```text
POST /api/auth/google
GET  /api/auth/session
POST /api/auth/logout
```

### POST /api/auth/google

Input:

```json
{ "credential": "<Google ID token>" }
```

Response:

```json
{
  "authenticated": true,
  "user": {
    "email": "...",
    "name": "..."
  }
}
```

Cookie set server-side. Raw Google credential is never returned or persisted.

### GET /api/auth/session

Authenticated:
```json
{
  "authenticated": true,
  "user": { "email": "...", "name": "..." },
  "csrfToken": "..."
}
```

Unauthenticated:
```json
{ "authenticated": false }
```

### POST /api/auth/logout

Requires valid session + CSRF; clears session cookie.

## 4. Shared private authorization

Current auth implementations:
- `apps/api/src/weread/private-auth.ts`
- `apps/api/src/s32/routes/private-auth.ts`

Do not duplicate Google/session verification independently in both.

Introduce a shared request-level decision:

```text
authorizePrivateRequest(req, capability)
  ├─ valid bearer/X-Private-Token for that capability → PASS
  └─ valid owner web session (+ CSRF when unsafe) → PASS
```

Capability must remain explicit:

```text
WEREAD_PRIVATE
S32_PRIVATE
```

A WeRead bearer token must not authenticate S32, and an S32 bearer token must not authenticate WeRead.

The Google owner session may authenticate both.

Preserve:
- current 401/403/404/503 behavior as closely as practical;
- no-store headers;
- auth before store/database access;
- auth before unsafe path decoding/body processing where existing M2-E guarantees require it.

## 9. Test plan

### 9.1 Google verifier
- valid exact audience/sub → PASS;
- wrong audience → deny;
- wrong owner sub → 403;
- expired/invalid token → deny;
- no token contents logged.

Mock Google verifier at route unit boundary; keep one integration test around the real library contract without network where possible.

### 9.2 Session
- valid signed cookie;
- tamper rejection;
- expiry rejection;
- wrong version rejection;
- Secure/HttpOnly/SameSite/Path attributes;
- logout clears;
- no secret fields.

### 9.3 CSRF
Cookie session:
- GET allowed;
- POST exact Origin + CSRF allowed;
- missing/wrong Origin denied;
- missing/wrong CSRF denied.

Bearer:
- existing POST behavior stays green without CSRF.

### 9.4 Auth separation
- WeRead token works only WeRead;
- S32 token works only S32;
- Google owner session works both;
- non-owner Google session works neither;
- auth failure causes zero S32 store / PG access.

### 9.5 Web
- logged out research page shows Google login, not token input;
- logged out WeRead Center shows Google login, not token input;
- login success updates both areas without re-entering credentials;
- logout removes access from both;
- refresh restores session through `GET /api/auth/session`;
- no raw private tokens in static bundle;
- no Google ID token persisted.

### 9.6 Regression
- existing WeRead private API tests;
- existing S32 M1/M2 auth/routes;
- M2-E malformed JSON / auth-before-parser guarantees;
- Web research suite;
- WeRead suite;
- API/Web builds.
